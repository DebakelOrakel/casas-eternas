# docs/

Developer documentation — English. PUBLIC IN PRINCIPLE (stated 2026-08-12):
everything here may appear on a future doc site. Game design material lives
outside the repository, because the game never states its ideas outright.
Nothing ships any of this *yet*; the layout (and
the one *planned* player-facing addition) is decided in
[decisions/documentation-architecture.md](./decisions/documentation-architecture.md).

## Folders

| Path | What it holds |
|---|---|
| [vision.md](./vision.md) | The Vision™ — a **human document**, not maintained by tooling or agents. |
| [decisions/](./decisions/) | One doc per decided fork: the options, the chosen answer, and why. Self-dating via front matter. |
| [design/](./design/) | How pieces fit together, and directions from design discussions — architecture notes and idea sketches that may precede any decision. Docs grow over time. |
| [changelog/](./changelog/) | Categorized human changelog ("*when* did this arrive"), one file per area — see its own [README](./changelog/README.md). |
| [operations/](./operations/) | The operator's manual — per-environment guides (local, Docker, Kubernetes). Its CLI/config reference pages are never written: the site renders them from `cli-reference.json`, generated by `tools/clidump` and drift-guarded by `make lint`. No stage/status front matter — a manual is always current. |
| [handbook/](./handbook/) | The player-facing manual, `en/` and `de/`, anchor IDs shared with the i18n key namespace — see its own [README](./handbook/README.md). |

## decisions/ vs. design/

The split is by **genre**, not by how far along something is. A **decision** doc
records one fork: the options, the chosen answer, and why. A **design** doc is a
map or a plan — how pieces fit together, or the essence of a design discussion
spanning many concerns. When a single fork inside a design discussion is big
enough to stand alone, it gets its own doc in `decisions/` (as
[decisions/server-users.md](./decisions/server-users.md) grew out of
[design/access-control.md](./design/access-control.md)); a design doc may also
keep decided forks inline while they are parts of one coherent plan.

Lifecycle lives in the front matter (`stage`), never in the folder: both
folders legitimately hold everything from an idea to a built system, and
decision docs are living documents — addenda and dated revisions are the norm,
not an exception. Where a doc stands in words is its last chapter, `## Status`.

## Front matter convention

Every doc in `decisions/` and `design/` starts with:

```yaml
---
id: DEC-0032                # DEC- in decisions/, DES- in design/, four digits
title.en: The detail ladder
title.de: Die Detail-Leiter
summary.en: One or two sentences — enough to decide whether to open the doc.
summary.de: The same in German.
area: generator             # generator | ui | mechanics | concepts | platform — the changelog's vocabulary
stage: decided              # idea | decided | building | built | superseded
createdAt: 2026-10-01       # never changed
updatedAt: 2026-10-03       # when the doc last said something new; omit it and createdAt stands
supersededBy: DEC-0033      # only with stage: superseded
concepts: [generator.concept.detail-levels]   # handbook concepts this doc stands behind
related: [DEC-0031, DES-0022]                 # written once, on either side
---
```

- **The id** is a number per folder, given in the order the documents came
  into the repository (first commit; the same commit in name order). It is
  never reused and never changed, and it is how documents name each other
  in the front matter. The file name stays a slug, so links into a doc do
  not move. The site shows a doc as `DEC-0032 · The detail ladder`; the
  number is not written into the title.
- **The title** is `title.en`; the text starts without a heading of its own.
  The German title and summary are for the German handbook and site; the
  text itself stays English.
- **A list** is `[a, b]`; a long value continues on lines indented by two
  spaces. The parser is a tolerant line reader, not YAML, so summaries need
  no quoting (client/scripts/docsite.ts).
- **The other directions are derived**: what a doc supersedes, and the docs
  that name it as related, are worked out from `supersededBy` and `related`,
  never written twice.
- **`concepts`** names handbook anchors (`generator.concept.<file>`, or a
  catalog key such as `resource.carryingCapacity`). The concept's page in
  the handbook lists the docs that name it.

`stage` is the machine-readable lifecycle, deliberately coarse so it can stay
true — it changes maybe twice in a doc's life:

- `idea` — nothing decided or built
- `decided` — the fork is chosen, nothing (or almost nothing) built yet
- `building` — partially built; open steps remain
- `built` — what the doc records exists (for overview docs describing the
  current system, this is the normal stage)
- `superseded` — the **whole** doc is replaced; `supersededBy` names the
  successor. Partial supersession is common and stays prose in `## Status`.

`## Status`, the doc's last chapter, is free-form but honest; "BUILT AND DOES
NOT PAY YET" is a valid and valuable status. The site build refuses a doc
whose id, required fields or references are wrong. The front matter is data:
a date-ordered decisions overview, grouping by `area`, or graying out
superseded docs are *generated views* over it, never hand-maintained lists
(see [decisions/grouped-changelog.md](./decisions/grouped-changelog.md)).
